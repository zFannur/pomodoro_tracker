## 1. Резюме: три симптома и их настоящие причины

### Симптом 1 — «на телефоне приложение зависает, авторизация проходит несколько раз»

Это не один баг, а пять, наложившихся друг на друга.

| № | Причина | Вклад |
|---|---|---|
| **B4** | `SoundService.init()` синтезирует ~489 000 сэмплов **до** `runApp()`, каждый запуск | чёрный экран на старте |
| **B5** | Ещё 6 блокирующих `await` до `runApp()`: миграция, обход валта, три refresh | чёрный экран на старте |
| **B6** | Диалог Google сам порождает `resumed` → `onForeground()` → новый синк → новый диалог | петля авторизаций |
| **B7** | `connected` определён как «статус ≠ disconnected», поэтому `syncing` и `error` считаются живой сессией и не блокируют повторный вход | петля авторизаций |
| **B8** | `MobileSyncAuth.restore()` вопреки контракту показывает системный UI и не кеширует клиента | каждый проход синка = ещё один диалог |

Порядок событий на холодном старте Android:

```
иконка → чёрный экран (B4+B5, секунды)
      → runApp
      → init() → restore() → шторка Google           ← диалог №1
      → показ шторки даёт paused→resumed (B6)
      → onForeground → syncIfStale → connected=true, т.к. status=syncing (B7)
      → syncNow → busy → таймер на 5 с
      → пользователь выбрал аккаунт, синк №1 завершился
      → через 5 с срабатывает таймер → syncNow → restore() (B8)
      → шторка Google                                 ← диалог №2
      → и так по кругу, пока не совпадёт окно lastSync < 1 мин
```

### Симптом 2 — «сделанные с телефона не появляются на ПК»

Два независимых механизма, каждый достаточен сам по себе.

**Первый — телефон вообще ничего не отправляет (B3).** Одного `null` от
`restore()` хватает, чтобы статус стал `disconnected` навсегда до перезапуска:
`_schedule` и `syncIfStale` оба закрыты гвардом `if (state.connected)`. Дальше
телефон копит правки молча — `markDirty` срабатывает, но пуш не запускает никто.
Возврат только через ручную кнопку «Подключить».

**Второй — данные приезжают и тут же уничтожаются (B1).** Между `applyRemote`
и перечитыванием стейта кубитами есть окно. Любая правка задач или журнала в
этом окне пишет доsync-снимок, а `_updateGraves` считает пропавшие id
удалёнными и ставит на них **надгробия**. Дальше `delete-wins` вычищает записи
телефона и на ПК, и на телефоне — навсегда.

### Симптом 3 — «идущий или приостановленный помидор не отображается»

**Это не баг, а отсутствующая функция (B9).** Состояние таймера лежит в
`timer_state.json`, а синхронизируется ровно один файл — `data.json`. Поля
таймера в документе нет вообще, `data_merge.dart` слова `timer` не знает.
Идущий помидор физически не может доехать до второго устройства.

## 3. Критические

### B1. Окно между `applyRemote` и перечитыванием стейта ставит надгробия на приехавшие записи

**✅ Исправлено.** Порядок веток синка НЕ трогали (это дало бы пинг-понг синков — см. ниже). Вместо этого: `_mirrorAll` вынесен из критического пути (`unawaited`), а репозиторий теперь помнит, что именно он отдал наружу (`_servedTasks`, `_servedDays`). Запись хоронит только те записи, которые вызывающий реально видел; приехавшее синком сохраняется, даже если снимок кубита о нём не знает.

**Файлы:** `lib/services/drive_sync_service.dart:245,271,297` ·
`lib/data/json_data_repository.dart:194-204` · `lib/presentation/cubits/tasks_cubit.dart:684`
**Симптом:** 2. **Класс:** безвозвратная потеря данных.

**Механизм.** Во всех трёх ветках синка порядок такой:

```dart
await applyRemote(merged);              // _doc = новый документ (:201)
                                        // + _mirrorAll по ВСЕМ дням (:203)
final info = await store.update(...);   // сеть
await _finish(info.revision, epoch, now);
await onRemoteApplied();                // ← только здесь кубиты узнают о новых данных
```

С момента `_doc = doc` (json_data_repository.dart:201) документ уже новый, а
`TasksCubit.state.todo` и `JournalCubit.state.log` — ещё старые. Правка в этом
окне идёт через `saveTasks` (:215-227) или `saveDay` (:284-291), которые
**заменяют список целиком** снимком устаревшего стейта. Дальше
`_write(doc, before:)` → `_updateGraves` (:177-191) вычисляет
`before.difference(now)` и хоронит всё, что было в документе, но нет в снимке —
то есть ровно записи, приехавшие с телефона. `_purge` (data_merge.dart:51,176-189)
удаляет их безусловно, `delete-wins` от `localWins` не зависит.

**Важное уточнение проверяющего.** Опасны ровно два метода:

* `saveTasks` — губит **задачи** с телефона (`doc.days` он не трогает, сессии выживают);
* `saveDay` — губит **сессии журнала** телефона за текущий логический день.

`addSession` безопасен (перечитывает свежий документ и дописывает),
`saveSprint` безопасен (зовёт `_write(doc)` без `before`, надгробия не считаются).

**Окно шире, чем кажется.** Самая длинная его часть — не сеть, а `_mirrorAll`
**внутри** `applyRemote` (:203): по файловому чтению на каждый из ~300 дней
истории, до возврата управления. На длинной истории это дольше одного PATCH в Drive.

**Исправление.** Двумя правками, обе в `json_data_repository.dart`:

1. Вынести зеркалирование из критического пути — оно не обязано быть синхронным:

```dart
Future<void> applyRemote(String content) async {
  final doc = _Doc.decode(content);
  ...
  _doc = doc;
  unawaited(_mirrorAll(doc));   // было: await _mirrorAll(doc);
}
```

2. Закрыть окно принципиально — версия документа:

```dart
int _rev = 0;                       // ++ в _write и в applyRemote

// _load() отдаёт версию наружу; saveTasks/saveDay принимают её
// и при несовпадении возвращают Failure «данные обновились», а не пишут.
```

Минимальный вариант, если версионирование пока не делать: в `saveTasks` не
подменять списки снимком кубита, а применять к актуальному `_doc` дифф
(что добавлено / что удалено), — тогда чужие записи в принципе не попадают в
`before.difference(now)`.

**Чего делать НЕ надо.** Переносить `onRemoteApplied()` перед `store.update`
— решение выглядит очевидным, но вносит регрессию: `onRemoteApplied` =
`reloadVault` → `sprintCubit.refresh()` → `saveSprint` → `onSaved` →
`markDirty` → `_dirtyEpoch++`. Тогда в `_finish` (:309-318) условие
`fresh.dirty && _dirtyEpoch != epoch` станет истинным, `dirty` останется
взведённым, и каждый merge будет порождать лишний цикл синка. Плюс если
`onRemoteApplied` бросит до аплоада, `_finish` не выполнится, `meta.rev`
останется старым, и каждый следующий синк будет заново заходить в ветку
конфликта, перезаписывая `data_conflict.json`.

**Утешение:** `_backup` (:321-326) кладёт проигравшую сторону в
`data_conflict.json`. При `localWins` там лежат полные данные телефона.
Восстановление возможно — но только до следующего конфликта.

### B2. `_write` и `applyRemote` пишут в один и тот же `data.json.tmp`

**✅ Исправлено.** Одна очередь `_serial` на репозиторий (через неё ходят `_write`, `applyRemote` и миграция) плюс уникальное имя временного файла `data.json.<n>.tmp`.

**Файл:** `lib/data/json_data_repository.dart:167` и `:198`
**Класс:** порча файла, потеря всего состояния.

**Механизм.** В `_write` стоит комментарий «Своё имя .tmp: у синка своё
(.sync.tmp)» — **это неправда**: `applyRemote` на строке 198 использует ровно тот
же путь `'${file.path}.tmp'`. Очередь `_writeQueue` (tasks_cubit.dart:669)
защищает только `saveTasks` от `saveTasks`; журнал, спринты и `applyRemote`
идут мимо неё. `tmp.writeAsString(..., flush: true)` — это open с усечением →
write → flush → close, несколько точек await, так что два вызова реально
перекрываются, после чего каждый делает `rename`.

**Сценарий.** Идёт помидор, пользователь возвращается в приложение →
`resumed` → `syncIfStale` → пул → `applyRemote` начинает писать `data.json.tmp`.
В эту же секунду помидор дотикал → `addSession` → `_write` открывает **тот же**
`.tmp` с усечением. Первый `rename` переносит перемешанные байты в `data.json`,
второй падает `FileSystemException`. Итог: невалидный JSON → следующий `_load()`
получает `FormatException`.

**Исправление.** Одна очередь на репозиторий, через которую проходят все писатели:

```dart
Future<void> _io = Future.value();

Future<T> _serial<T>(Future<T> Function() body) {
  final next = _io.then((_) => body());
  _io = next.then((_) {}, onError: (_) {});
  return next;
}
```

`_write` и `applyRemote` целиком заворачиваются в `_serial`. Плюс уникальное имя
временного файла как страховка: `'${file.path}.${_writeSeq++}.tmp'`.

После этого очередь в `TasksCubit` (:669) становится избыточной — её можно снять.

### B3. Один `null` от `restore()` навсегда выключает автосинк

**✅ Исправлено.** Гварды в `_schedule` и `syncIfStale` смотрят на `_configured` (есть чем авторизоваться), а не на `connected`. Добавлен флаг `_offByUser`, чтобы явное «Отключить» не обходилось этим же путём.

**Файл:** `lib/presentation/cubits/sync_cubit.dart:61,67,99`
**Симптом:** 2 (основная причина), частично 1.

**Механизм.** `SyncOutcome.notConnected` → `status = disconnected` (:98-99).
После этого закрыты **все** автоматические пути:

* `_schedule` → `if (state.connected) unawaited(syncNow())` (:61) → false;
* `syncIfStale` → `if (!state.connected) return;` (:67).

Вход обратно только через кнопку «Подключить» (:89) или перезапуск процесса.
А `notConnected` возвращается каждый раз, когда `auth.restore()` отдал null —
на Android это штатная ситуация: пользователь смахнул шторку, или
`authorizationForScopes` не отдал разрешение без интерактива.

**Сценарий.** Телефон, синк ранее настроен. Старт → шторка Google → пользователь
её смахнул → `disconnected`. Дальше весь сеанс: закрыл 5 задач, написал заметки —
каждая правка честно зовёт `markDirty`, взводит таймер, таймер срабатывает и
**молча ничего не делает**. Пользователь уверен, что синк работает.

**Исправление.**

```dart
// Развести «настроен» и «есть живая сессия».
bool get _configured => Platform.isWindows
    ? _settings().syncClientId.trim().isNotEmpty
    : _settings().syncServerClientId.trim().isNotEmpty;

// В _schedule и syncIfStale проверять _configured && !_userDisconnected,
// а не state.connected.
```

При `notConnected` — не гасить статус навсегда, а планировать повтор с
нарастающей задержкой и **показать видимый баннер** «синк отключён, нажмите
Подключить» в шапке, а не только в диалоге настроек.

**Осторожно (замечание проверяющего).** Признак «настроен» переживает явное
`disconnect()` (:133-137 сбрасывает только состояние кубита, поля настроек
остаются). Поэтому нужен отдельный флаг «пользователь отключил вручную»,
иначе после нажатия «Отключить» таймер будет каждые 5 секунд лезть в
`syncNow()` и дёргать Google-диалог.

## 4. Высокие

### B4. `SoundService.init()` пересинтезирует ~489 000 сэмплов на каждом запуске, до `runApp()`

**✅ Исправлено.** Значения map стали тир-оффами `List<double> Function()`, синтез идёт только при отсутствующем файле. Плюс сам `sound.init()` убран с пути к первому кадру.

**Файл:** `lib/services/sound_service.dart:22` · вызов `lib/main.dart:79`
**Симптом:** 1.

Литерал map (:22-34) вычисляется **целиком и сразу**: все 11 генераторов
отрабатывают до того, как строка 39 проверит `if (!await file.exists())`.
Каждый сэмпл — 1–3 вызова `math.sin`/`math.exp`, результат складывается в
`List<double>` — это боксированные double, ~12 МБ аллокаций одним синхронным
всплеском на UI-изоляте. На втором и всех последующих запусках работа
выбрасывается целиком: файлы уже на диске.

Объём подтверждён размером готовых файлов: 978 КБ PCM16 = ~489 000 сэмплов.

**Исправление** — ленивые тир-оффы, три строки:

```dart
final sounds = <String, List<double> Function()>{
  FinishSound.bell.name: _bell,
  ...
  'tick': _tick,
};
for (final entry in sounds.entries) {
  final file = File('${dir.path}${Platform.pathSeparator}sound_${entry.key}.wav');
  if (!await file.exists()) {
    await file.writeAsBytes(_wav(entry.value()), flush: true);
  }
  _paths[entry.key] = file.path;
}
```

Инвариант «`_paths` заполняется для всех 11 имён всегда» сохраняется — от него
зависят ранние выходы `playFinish`/`playTick` (:48,57).

**Не делать `unawaited(sound.init())`** — само по себе не работает: `init()`
выполняется синхронно до первого await, то есть весь синтез всё равно
случится на старте, только без гарантии готовности звука.

### B5. Шесть блокирующих `await` до `runApp()`

**✅ Исправлено.** `runApp` идёт первым, вся загрузка — в `bootstrap()` после первого кадра. Дефолт `mirrorToVault` стал `Platform.isWindows` (одна строка в `app_settings.dart`, тумблер в настройках остаётся живым).

**Файл:** `lib/main.dart:213-221` против `:225`
**Симптом:** 1.

До первого кадра последовательно: `tasksCubit.load()` (на первом запуске —
`_migrate()` с рекурсивным обходом всего журнала валта), `drainInbox()`
(чтение + запись файла), `rolloverCheck()` (ещё запись), `Future.wait` из
трёх refresh (в котором `statsCubit.refresh()` берёт диапазон ~60 дней, а
`sprintCubit.refresh()` ещё и **пишет** документ), `timerCubit.restore()`.

Плюс: `mirrorToVault` по умолчанию `true` и на Android тоже
(app_settings.dart:224), а корнем валта там становится
`getApplicationDocumentsDirectory` — где никакого Obsidian нет. Зеркала
пишутся вникуда, но время тратят.

**Исправление.**

1. Дефолт зеркала по платформе — одна строка в `app_settings.dart:224`:
   `json['mirrorToVault'] as bool? ?? Platform.isWindows`.
   (Не `mirrorEnabled: () => Platform.isWindows && ...` в main.dart — это
   сделает тумблер в настройках мёртвым и отрежет macOS/Linux, где валт возможен.)
2. `runApp` сразу, а `load`/`refresh`/`restore` — после первого кадра. Кубиты
   уже имеют `status: loading`, и UI умеет его показывать: стартовый экран
   перестанет быть чёрным.

### B6. Диалог Google сам порождает `resumed` → новый синк → новый диалог

**✅ Исправлено.** На `busy` больше не взводится слепой таймер: ставится флаг `_pending`, и повтор происходит один раз по завершении текущего прохода. Плюс `syncIfStale` выходит, если проход уже идёт.

**Файл:** `lib/main.dart:286-290`, `:206-209`
**Симптом:** 1.

На Android шторка Credential Manager — отдельная активность: её показ переводит
MainActivity в `paused`, закрытие — в `resumed`. `didChangeAppLifecycleState`
на каждый `resumed` зовёт `onForeground()` → `syncIfStale()`. То есть **сам факт
показа диалога гарантированно запускает новый синк**. Спасает только `_running`
(drive_sync_service.dart:202), но `busy` перевзводит таймер на 5 с, и как только
первый проход завершится — таймер выстрелит и покажет шторку снова.

**Исправление.** Ключевая правка — не в `main.dart`, а в кубите: **не взводить
слепой таймер на `busy`**. Вместо `_schedule(5s)` поставить флаг
`_pending = true` и проверять его в конце текущего `sync()` — тогда повтор
происходит ровно один раз и ровно тогда, когда есть что отправлять.

Дополнительно: подавлять `onForeground` на время интерактивного входа
(флаг `authInFlight` в `SyncAuth`).

### B7. `connected` = «статус ≠ disconnected»

**✅ Исправлено.** Появилось отдельное поле `hasSession`, `connected` считается по нему. Ветка `busy` при этом не сломалась — она теперь идёт через `_pending`, а не через гвард.

**Файл:** `lib/presentation/cubits/sync_cubit.dart:24`
**Симптом:** 1.

`bool get connected => status != SyncStatus.disconnected;` — значит `syncing`
и `error` тоже считаются «подключено». А `syncNow()` эмитит `syncing` **первой
строкой** (:94), до того как узнал, есть ли вообще сессия. Отмена входа даёт
`error` — тоже «подключено». В обоих случаях гварды `if (state.connected)`
перестают защищать.

Побочно ломается UI: `settings_dialog.dart:763` рисует кнопку «Подключить»
только при `!sync.connected` — после ошибки входа кнопка исчезает.

**Исправление.** Отдельное поле `hasSession`, выставляется только после успешного
исхода; `connected` считать по нему.

**Осторожно (замечание проверяющего).** Если выставлять `hasSession` строго
после `pushed/pulled/merged/noChanges`, ломается ветка `busy`: во время первого
незавершённого синка `hasSession == false`, и дебаунс, взведённый стартовым
`rolloverCheck` → `onSaved` → `scheduleSync`, отвалится по гварду и не
перевзведётся. Данные не потеряются (`markDirty` уже персистится), но пуш
задержится — а это ровно жалоба №2. Нужно, чтобы `busy` обрабатывался по
`_pending`, а не по гварду `connected` (см. B6).

### B8. `MobileSyncAuth.restore()` нарушает контракт «тихо, без UI» и не кеширует клиента

**✅ Исправлено.** Кешируется `GoogleSignInAccount`, а НЕ `http.Client` (у него нет refresh-токена и фальшивый срок в 365 дней — закешированный клиент начал бы молча отдавать 401). При `authorizationForScopes == null` кеш аккаунта сбрасывается.

**Файл:** `lib/services/sync_auth.dart:177-190`
**Симптом:** 1 и 2.

`WindowsSyncAuth` кеширует клиента в `_client` (:56, проверка :72-74).
`MobileSyncAuth` кеша не имеет: каждый вызов — `attemptLightweightAuthentication()`
+ `authorizationForScopes()`, а на Android это системный UI.

**Исправление — НЕ простое кеширование `http.Client`.** Проверяющий нашёл мину:
`authz.authClient(scopes:)` из `extension_google_sign_in_as_googleapis_auth 3.0.0`
строит `AccessCredentials` с **`refreshToken = null`** и **выдуманным
`expiry = now + 365 дней`** (в пакете прямо написано: «The underlying SDKs don't
provide a refresh token»). Закешировать такой клиент — значит: реальный токен
протухнет через час, `googleapis_auth` не обновит его (нечем) и не заметит
протухания (expiry фальшивый), и каждый вызов Drive начнёт валиться 401.
Обработки 401 нет нигде — синк тихо умрёт до перезапуска.

Правильный вариант:

* кешировать **`GoogleSignInAccount`**, а не `http.Client`;
* `authorizationForScopes` вызывать на каждый проход (он дёшев и не показывает
  UI, если разрешение уже есть), но клиент строить заново;
* добавить обработку 401 в `DriveRemoteStore`: сбросить кеш аккаунта и вернуть
  `notConnected` вместо тихой смерти.

### B9. Состояние таймера не входит в синхронизируемый документ

**✅ Реализовано.** В `data.json` появилась секция `timer`, в слиянии — правило «побеждает больший `savedAt`». Снимок публикуется ТОЛЬКО на переходах (старт/пауза/резюм/стоп/смена фазы), периодические сохранения раз в 15 секунд по-прежнему идут в локальный `timer_state.json` — иначе был бы аплоад в Drive каждые 15 секунд. Чужой помидор показывается с подписью «идёт на другом устройстве», тикает от настенных часов, но НЕ завершается и записи в журнал не делает: её сделает то устройство, где он запущен. Любое локальное действие забирает управление себе.

**Файлы:** `lib/data/timer_state_store.dart:60-67` · `lib/main.dart:188`
**Симптом:** 3. **Класс:** отсутствующая функция, не регрессия.

Синкается ровно один файл — `data.json` (drive_sync_service.dart:141).
Документ состоит из `todo/planner/days/sprints/graves/rollover`
(json_data_repository.dart:545-564), полей таймера там нет. `mode`, `run`,
`remaining`, `total`, `series`, `interruptions`, `delaysMs` не покидают
устройство никогда. `series` тоже локальна — после перехода на другое
устройство сбивается каденс длинного перерыва.

**Исправление — отдельная задача, не однострочник.** Эскиз:

* объект `timer` в `data.json` с полями `deviceId`, `savedAt`, `startedAt`, `overtime`;
* в `data_merge.dart` — отдельное правило: не union, а «побеждает снимок с бо́льшим `savedAt`»;
* в `TimerCubit` — `adoptRemote(...)`, пересчитывающий `remaining` от настенного
  времени; при чужом `deviceId` показывать read-only («идёт на другом
  устройстве»), чтобы два устройства не тикали один помидор наперегонки.

**Главный риск (замечание проверяющего): амплификация записи.**
`_periodicSave()` (timer_cubit.dart:493-496) пишет снимок **каждые ~15 секунд
всегда** — тикер запускается безусловно в `restore()` (:214) и живёт до закрытия
приложения, а `_tick()` при остановленном таймере всё равно эмитит и зовёт
`_periodicSave()` (:355-361). Если перенести снимок в `data.json` как есть,
каждая такая запись пойдёт через `_write` → `onSaved` → `scheduleSync` →
полный раунд-трип в Drive. Получится ~4 записи файла и до 4 аплоадов в минуту,
круглосуточно. Прежде чем переносить — обязательно развести «состояние таймера»
и «повод для синка»: либо `_write` без `onSaved` для таймерной секции, либо
отдельный дебаунс на минуту-две.

### B10. Надгробие переживает восстановление из корзины

**✅ Исправлено.** Выбран дешёвый вариант: восстановление из корзины выдаёт задаче новый id. Дорогой (`revived`-метки) отклонён — он потребовал бы поля в `_Doc`, веток в decode/encode и TTL, а без этого был бы инертен.

**Файлы:** `lib/data/data_merge.dart:138-151` · `lib/data/json_data_repository.dart:185`
**Класс:** потеря данных.

`_updateGraves` при локальной записи снимает надгробие
(`doc.graves.removeWhere((id, _) => now.contains(id))`). Но `_mergeGraves` —
чистое **объединение** надгробий обеих сторон, признака «воскрешения» в формате
нет. Надгробие, уже уехавшее на второе устройство, возвращается при первом же
слиянии, и `_purge` снова удаляет восстановленную запись.

**Сценарий.** ПК: удалили задачу X → надгробие ушло в Drive → телефон его
получил. Через минуту на ПК «Корзина → Восстановить» → X жива, надгробие снято
локально. Телефон при следующем синке (он не dirty) идёт в pull-ветку:
`_mergeGraves(remote={}, local={X})` → надгробие выживает → X удаляется на
телефоне. Любая правка на телефоне отправит его документ с надгробием обратно —
и на ПК X исчезнет окончательно.

**Исправление — дешёвый вариант.** При восстановлении из корзины выдавать
задаче **новый id**: `task.copyWith(id: newId())`. Старое надгробие никого не
задевает. Одна строка в `TasksCubit.restoreFromTrash` (:512).

**Дорогой вариант (`revived`-метки) требует больше, чем кажется.**
`mergeData` сохраняет незнакомые ключи победителя (`{...winner}`), но
`_Doc.decode`/`_Doc.encode` (:480-524, :543-565) имеют **жёстко фиксированный
набор ключей**, и `applyRemote` делает `decode` → `encode` в ту же секунду.
Любая новая секция, не заведённая в `_Doc`, стирается немедленно. Это отдельный
структурный вывод — см. B23.

### B11. rollover-флаги не синхронизируются, а `rolloverCheck` выполняется до первого синка

**✅ Исправлено.** Отметки переехали в `doc.rollover` (`markRollover`/`rollover` в репозитории), из `AppSettings` больше не читаются. `rolloverCheck` выполняется после ПОПЫТКИ первого синка (с потолком 20 секунд, чтобы отсутствие сети его не блокировало) и по-прежнему до `sprintCubit.refresh()`.

**Файлы:** `lib/main.dart:126-139,213-215` · `lib/data/json_data_repository.dart:517-522,564`
**Класс:** потеря пользовательского выбора.

Признак смены дня/недели берётся из `AppSettings` (`lastDay`, `lastSprintId`),
а настройки в синк не входят. При этом в документе **есть готовое место**:
`_Doc.rollover` декодируется, кодируется и аккуратно мержится
(`_mergeRollover`, data_merge.dart:156-173) — и даже покрыто тестом
(data_merge_test.dart:221). Но **туда никто никогда не пишет**. Поле мёртвое.

**Сценарий.** Понедельник 09:00, ПК: новая неделя → `clearWeekFlags` →
пользователь ставит ⭐ на 3 задачи спринта → пуш. Понедельник 20:00, телефон:
старт читает старый локальный `data.json` → `rolloverCheck` видит свой
`lastSprintId` = прошлая неделя → `clearWeekFlags` снимает ⭐ → пишет файл →
**только после этого** стартует синк → локальный mtime свежее → `localWins` →
у совпадающих id остаётся версия телефона с `week: false`. Три ⭐, выбранные

**Исправление.**

1. Писать `doc.rollover['day']` / `['week']` через репозиторий — поле и merge
   уже готовы, нужен только писатель. `lastDay`/`lastSprintId` из `AppSettings` убрать.
2. Выполнять `rolloverCheck` **после попытки** первого синка.

**Осторожно (замечание проверяющего).** Именно «после попытки», а не «после
успешного синка»: иначе при `notConnected` или проглоченном исключении rollover
не выполнится вовсе, и 🐸/⭐ перестанут сбрасываться на устройстве без сети.
Плюс не забыть явно задокументированный инвариант main.dart:211-212 — rollover
обязан идти **до** `sprintCubit.refresh()`, иначе файл новой недели создастся со
звёздами прошлой.

### B13. `TimerSnapshot` не хранит `overtime` и `startedAt`

**✅ Исправлено.** Добавлены `overtime` и `startedAt`; в `restore()` овертайм проверяется ОТДЕЛЬНОЙ веткой до расчёта остатка. Заодно снимок пишется атомарно.

### B15. Таймер считает тики, а не настенное время

**✅ Исправлено.** Источник истины — `_phaseEnd`, остаток считается от `clock.now()`. Взят `package:clock`, а не `DateTime.now()`: `fake_async` подменяет только его, иначе все таймерные тесты бы упали.

**Файл:** `lib/presentation/cubits/timer_cubit.dart:213-215,369`

Единственный источник отсчёта — `Timer.periodic(1s)`, а `_tick()` уменьшает
счётчик арифметически. Пропущенные тики Dart не догоняет: при заблокированном
event loop `Timer.periodic` коалесцирует пропуски в один колбэк. Сверка с
реальным временем есть только в `restore()`.

**Сценарий (детерминированный).** Windows: помидор 25:00, через 5 минут ноутбук
уходит в сон на 20 минут. После пробуждения на экране 20:00, и таймер считает
дальше с этого места — помидор реально длится 45 минут вместо 25. В журнал
уходит `workedMinutes = total/60 = 25`, а `startedAt` — 45 минут назад.

**Исправление.** Настенное время как источник истины: хранить `_startedAt` +
накопленную паузу, в `_tick()` вычислять
`remaining = total - now.difference(_startedAt).inSeconds + pausedSeconds`,
тик использовать только как триггер перерисовки. Плюс пересчёт по `resumed`
и `onWindowFocus`.

**Осторожно (замечание проверяющего).** `DateTime.now()` в `_tick()` **сломает
все таймерные тесты**: `fake_async` подменяет только `clock.now()` из
`package:clock`, но не `DateTime.now()`. Использовать `clock.now()` и добавить
`package:clock` в зависимости.

## 5. Средние

### B16. Сортировка сессий при слиянии ломает границу логического дня

**✅ Исправлено.** Сортировка по логической минуте дня. Граница 05:00 вынесена в единственную константу `dayStartHour` — она была вписана в четыре файла, и сортировка про неё не знала.

**Файл:** `lib/data/data_merge.dart:110`

`..sort((a, b) => '${a['t']}'.compareTo('${b['t']}'))` — лексикографически по
`HH:mm`. Но день длится 05:00→05:00, и часы 0–4 хронологически стоят **в конце**
дня. Сортировка загоняет их в начало.

Последствия: кривой порядок в зеркале журнала и — важнее — `_writeHistory`
берёт `log.sessions.last` как «предыдущий помидор» для антинакрутки
(tasks_cubit.dart:601-606), а после пересортировки это уже не последняя запись.

**Исправление.**

```dart
int slot(Object? t) {
  final p = '$t'.split(':');
  final h = int.tryParse(p.first) ?? 0;
  final m = p.length > 1 ? int.tryParse(p[1]) ?? 0 : 0;
  return ((h < 5 ? h + 24 : h) * 60) + m;
}
..sort((a, b) => slot(a['t']).compareTo(slot(b['t'])));
```

Плюс независимо: в `_writeHistory` брать не `sessions.last`, а максимум по `start`.

*Замечание:* это копирует магическую «5» в четвёртое место. Правило 05:00 уже
живёт в `logicalDate` и в `_sessionFrom` — стоит вынести его в одну константу.

### B17. Веха спринта стирается при слиянии, если у победителя ключа нет

**✅ Исправлено.** База слияния стала `{...l, ...w}` — одна строка.

**Файл:** `lib/data/data_merge.dart:132`

`{...w, 'done': ...}` — «скаляр победителя» реализован как «ключ победителя».
Но `_Doc.encode` пишет `milestone` только когда он непустой
(json_data_repository.dart:559). У устройства с пустой вехой ключа в JSON просто
**нет**, и `{...w}` даёт результат без вехи — непустая веха проигравшего исчезает.

**Исправление — одна строка:**

```dart
result[key] = {...l, ...w, 'done': _mergeValues(w['done'], l['done'])};
```

`{...l, ...w}` уже даёт значение проигравшего там, где у победителя ключа нет.
То же правило применимо в `_mergeDays` для полей, которые `encode` умеет опускать.

### B18. У прохода синка нет таймаута

**✅ Исправлено.** Таймауты на каждом сетевом вызове (30 с) и на авторизации (3 мин). Внешнюю обёртку `.timeout()` не ставили — она не отменяет внутренний future и `_running` бы не снялся.

**Файл:** `lib/services/drive_sync_service.dart:202,302-304`

`_running` снимается в `finally`, то есть когда завершится каждый await внутри.
Ни один не ограничен по времени: `auth.signIn()`/`restore()` ждут системный
диалог сколько угодно, вызовы `googleapis` идут без `.timeout(...)`. Зависший
сокет оставляет `_running = true` навсегда — дальше каждый `sync()` возвращает
`busy`, и «Синхронизировать» в настройках перестаёт работать.

**Исправление.** Внешний `.timeout()` на обёртке **не помогает**: `Future.timeout`
не отменяет внутренний future, `finally` не выполнится. Таймауты нужны на
**каждом** сетевом вызове внутри: `.timeout(const Duration(seconds: 30))` на
`store.find/download/update`. Для интерактивного входа — длиннее (2–3 мин), но конечный.

### B19. Миграция из markdown выдаёт задачам новые id → дубликаты после синка

**✅ Исправлено.** Задачам из зеркала выдаются детерминированные id (`md-t<i>`/`md-p<i>`) — тот же приём, что уже применён к сессиям журнала. Путь миграции при этом сохранён.

**Файл:** `lib/data/json_data_repository.dart:105-109`

`planLine` (markdown_codec.dart:111-119) не пишет id — в зеркале `Задачи.md`
идентификаторов нет. `_migrate()` при отсутствии `tasks.json` читает зеркало и
раздаёт каждой задаче свежий `newId()`. Для сессий журнала это решено
(детерминированные id `m<дата>-<HHmm>-<n>`), для задач — нет.

**Сценарий.** Переустановка или вторая машина с тем же валтом: 12 задач
поднимаются с 12 новыми id → первый синк объединяет по id → **24 задачи**,
а ранее удалённые воскресают.

**Исправление — самое простое:** не мигрировать задачи из markdown вовсе.
Зеркало объявлено односторонним, источник истины — `data.json`/`tasks.json`;
при их отсутствии честнее показать пустой список и дать синку принести данные
из Drive.

*Вариант «писать id в строку зеркала» имеет мину:* `_durationTailRe`,
`_categoryTailRe`, `_dueTailRe` (markdown_codec.dart:54-56) якорятся на `$`, а
`week` определяется через `rest.endsWith('⭐')`. Хвост `<!--id:abc-->` сломает
все четыре разбора, если не срезать его первым.

### B20. `_mirrorNote` перед `---` ломает `parseFrontmatter`

**✅ Исправлено.** Устойчивым сделан `parseFrontmatter` (пропускает пустые строки и HTML-комментарии), а не сериализаторы: в валте уже лежит вся история в текущем формате.

**Файл:** `lib/data/json_data_repository.dart:58`, использование `:422,427,435`

Зеркала пишутся как `_mirrorNote + serialize…`, то есть первой строкой идёт
HTML-комментарий, а `---` — второй. `parseFrontmatter` (markdown_codec.dart:165)
требует `---` **первой** строкой и на реальных файлах приложения всегда
возвращает пустую карту. Поэтому `parseSprint` отдаёт `goal = fallbackGoal` и
`milestone = ''`.

Тесты не ловят, потому что парсят голый сериализатор, а не то, что реально
пишется на диск.

**Исправление.** Сделать `parseFrontmatter` устойчивым — пропускать ведущие
пустые строки и HTML-комментарии до первого `---`. Именно так, а не «переставить
комментарий»: в валте уже лежит вся история в текущем формате, и правка
сериализаторов починит только те файлы, которые будут перезаписаны.
Плюс тест, который парсит `_mirrorNote + serializeSprint(...)`.

### B21. Правки журнала не обновляют статистику и спринт

**✅ Исправлено.** Добавлен `JournalCubit.onJournalChanged`, в `main.dart` он перечитывает статистику и спринт.

**Файл:** `lib/presentation/cubits/journal_cubit.dart:127-191`

`editEntry`, `deleteEntry`, `fillBlanks`, `clearToday`, `addNote` заканчиваются
на `saveDay` и никого не уведомляют. Для сравнения: `TasksCubit` после ручного
«сделано» специально дёргает `onHistoryWritten` (:369), который перечитывает
journal + stats + sprint.

**Исправление.** Тот же колбэк: `Future<void> Function()? onJournalChanged;`,
вызывать в конце `_saveDay` и `addNote`, назначать в `main.dart` рядом с
`tasksCubit.onHistoryWritten`.

### B22. `restore()` не защищён от отрицательной разницы времени

**✅ Исправлено.** Клампы (`left.clamp(0, total)`, отрицательный возраст обнуляется), а НЕ ранний `return` — тот терял бы восстановленный помидор при любой штатной коррекции часов.

**Файл:** `lib/presentation/cubits/timer_cubit.dart:168-169`

`age` проверяется только сверху (`> 1 час`). Отрицательный проходит дальше:
ветка running даёт `remaining > total`, `_startedAt` уезжает в будущее,
прогресс-бар становится отрицательным, а `delaysMs + age.inMilliseconds` —
отрицательным простоем, который уходит в журнал и ломает агрегаты фокуса.

**Исправление — клампы, а не `return`:**

```dart
remaining: left.clamp(0, saved.total),
delaysMs: math.max(0, saved.delaysMs + age.inMilliseconds),
```

**Не делать `if (age.isNegative) return;`** — любая штатная коррекция часов
назад (NTP, доли секунды) молча выбросит восстановленный помидор и серию:
`return` стоит до обоих фолбэков `emit(state.copyWith(series: saved.series))`.
Размен в минус.

### B23. Структурное: `_Doc` молча стирает секции, которых не знает

**✅ Исправлено.** У `_Doc` появилась карта `extra` для незнакомых ключей, она выводится обратно в `encode`.

**Файл:** `lib/data/json_data_repository.dart:480-524,543-565`

`mergeData` специально сохраняет незнакомые ключи победителя
(`{...winner}`, с комментарием, что иначе «любая секция молча исчезала бы»).
Но `_Doc.decode`/`_Doc.encode` имеют жёстко фиксированный набор ключей, а
`applyRemote` делает `decode` → `encode` немедленно. **Защита в `mergeData`
не работает**: всё, что не заведено в `_Doc`, стирается в ту же секунду.

Это не отдельный симптом сегодня, но это ловушка для каждой будущей секции
(`revived`, `timer`, что угодно). Либо завести в `_Doc` карту `_extra` для
неизвестных ключей и выводить её в `encode`, либо убрать вводящий в заблуждение
комментарий из `data_merge.dart:34-36`.

### B24. `prolong()` не сохраняет снимок

**✅ Исправлено.** Одна строка `_save()` в `prolong()`; `_phaseEnd` при этом тоже сдвигается.

**Файл:** `lib/presentation/cubits/timer_cubit.dart:307-314`

Периодическое сохранение — раз в 15 тиков; `prolong()` не зовёт `_save()` вовсе.
Нажал «+5 мин», через 3 секунды свернул приложение, ОС убила процесс → помидор
закончится на 5 минут раньше.

**Исправление — одна строка:** `_save()` в конце `prolong()`.
Остального (сохранение по `paused`/`inactive`, снижение периода до 5 тиков)
не требуется: проверяющий показал, что сохранение при входе в овертайм —
мёртвый код, а лайфсайкл-хуки на Android не гарантируют выполнения.
